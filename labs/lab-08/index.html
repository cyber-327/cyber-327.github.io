Lab 08 · Week 8 · October 23, 2026

DC-08: Maintenance Port Investigation

Investigate the DC-08 maintenance interface, construct command packets, and test three successive security patches

Learning Outcomes

By the End of This Lab

  • Decode hex clues and identify an eight-byte message format
  • Demonstrate a detected one-bit change and an undetected two-bit parity change
  • Create a changed command with a matching CRC using the supplied calculator
  • Find a different command with the same approved CRC while keeping the correct device ID
  • Separate error-check consistency, command acceptance, and authorized origin

The Big Picture

What You Are Doing

  1. Your team has access to the DC-08 maintenance interface. Recover its service documentation and determine how to issue an accepted OPEN command.
  2. Red indicates LOCKED. Green indicates OPEN. Successful commands trigger successive firmware patches; complete all three to leave the controller unlocked.
  3. Recover a leaked service-sheet address from hex output, then use the service sheet to learn the packet format.
  4. Patch v1.0 checks even parity. Patch v2.0 uses CRC. Patch v3.0 changes the CRC convention and also requires an approved CRC value. Record each flag and the next patch capture.
  5. Use the workbench to decode fields and calculate CRCs with parameters from the schematic. Determine parity yourself. Record the controller's serial response, not just a calculator match.

Before Lab

Preparation

  • Review even parity, CRC parameters, and the difference between error detection and authentication.
  • Open the Lab 8 report and packet workbench. Only the computer attached to the Nano needs Arduino IDE and Serial Monitor. Ask the instructor for a prepared computer if the application or board port is unavailable.
  • Use the prepared DC-08 firmware. Do not upload another sketch, inspect firmware for flags, or bypass the maintenance interface by driving LED pins.

Bench Setup

Equipment and Materials

  • Per team: instructor-prepared classic 5 V Arduino Nano and USB data cable
  • Computer with Arduino IDE Serial Monitor and a browser for the packet workbench
  • Breadboard, red LED, green LED, two 330 ohm resistors, and jumper wires, prechecked by the instructor
  • Lab 8 report and packet workbench

Follow These Steps

Lab Walkthrough

1. Discover the Maintenance Port — Table 1

Evidence Photo

Save the decoded service address, your constructed INIT packet, and the first version/device header and LOCK capture.

  1. Disconnect USB before checking wiring. D4 drives red and A5 drives green; each LED has its own 330 ohm resistor to its anode, with its cathode connected to GND. Use USB power only.
  2. Connect USB. Open Serial Monitor at 115200 baud, 8-N-1, with a newline at the end of each message. Do not upload a sketch. Close other programs using that serial port.
  3. Before initialization, the controller outputs only an address in hex, immediately and every 10 seconds. Save one copy and decode it with the converter.
  4. Open the decoded address and recover the service schematic. Use its command list and service addressing/parity rules to construct an INIT packet in the correct syntax. Send your packet to initialize the controller; do not type the bare word INIT.
  5. Every command is one line of 16 hex digits, with optional spaces. INIT, HELP and RSET use service ID 00, zero extra bytes and even parity in every patch. LOCK/OPEN use the discovered device ID. Record the version header and LOCK packet emitted after INIT; the capture repeats every 30 seconds.

2. Patch v1.0: Satisfy Parity — Table 2

Evidence Photo

Preserve one failed parity test and the patch-1 OPEN result. Label the changed bits and record serial text, not color alone.

  1. Capture the v1.0 LOCK packet and load its eight bytes into the workbench. The check byte must be 00 or 01 and make the total number of one bits even.
  2. Send the captured LOCK message. It should be accepted while the red LED stays on. A valid message is not necessarily an OPEN command.
  3. Restore the capture before each test. Flip one bit in an extra byte without changing the check and send it. Record the failure reason and restart. Send INIT again, restore the original capture, then flip two bits in an extra byte while keeping the check and test again. Keep the ID and command unchanged.
  4. Build an OPEN packet for your device and determine its even-parity check manually. Inspect the command, then send it. Save this successful packet and the flag. Green illuminates during patch installation; wait for Patched! and the v2.0 header before continuing.

3. Patch v2.0: Recompute the CRC — Table 3

Evidence Photo

Save the changed command with the old CRC failing and the matching new CRC succeeding.

  1. Capture the v2.0 LOCK packet. Enter all five v2.0 CRC parameters from the schematic into the calculator. Calculate over bytes 0–6, including both extra bytes; byte 7 stores the check and is excluded.
  2. Change only the four command bytes to OPEN and retain the old check. Send it and record the failure. Wrong input returns to before INIT at v1.0: send INIT, replay your saved v1.0 OPEN packet and wait for the v2.0 capture before retrying.
  3. Choose Calculate CRC, then enter the calculated byte into byte 7 yourself. Inspect and send the OPEN packet. Save this successful packet and flag, then wait for v3.0. Changing both message and check is recomputation; the next patch requires keeping an approved check fixed.

4. Patch v3.0: Keep an Approved CRC — Table 4

Evidence Photo

Save the approved baseline, a rejected unapproved-CRC attempt, the helper's collision result, and the Arduino's successful patch-3 response.

  1. Capture the v3.0 LOCK packet and record its device ID, extra bytes and approved CRC. Update all five calculator parameters for v3.0, which uses a different CRC convention. Use this capture, not the v2.0 CRC.
  2. Change the command to OPEN, retain both extra bytes, and calculate its v3.0 CRC. Send the otherwise-valid packet and record the approval failure. To return to v3.0, send INIT and replay your saved successful v1.0 and v2.0 OPEN packets, waiting for each patch installation.
  3. Restore the approved CRC into byte 7. Set the command to OPEN, then lock every digit except the four digits of the two extra bytes. The helper's Vary extra bytes only button sets those locks without changing your values. Both check digits must remain locked.
  4. Run the fixed-CRC search. Record the locked fields, approved CRC, matching packet, and number of candidates tested. Two extra bytes give 65,536 combinations and 256 matching combinations for each target CRC when both are fully adjustable. The starting packet is excluded; if it already matches, 255 different matches remain. Use Next collision to cycle through the results.
  5. Inspect the result: its command must decode to OPEN, its device ID must match, and its CRC must equal the current approved value. A matching LOCK stays locked. Send the OPEN result; record the third flag, Congratulations! and the green LED remaining on. A correctly formed RSET packet starts a new run.

5. Explain the Trust Boundary

  1. Compare the three patches. Which tested accidental changes did each notice? Why could a deliberate sender still create an accepted OPEN command? Do not claim parity or CRC protects all error patterns.
  2. Explain why approving a CRC value does not approve one particular command. Restrict testing to your assigned controller and maintenance interface.
  3. Propose a keyed message-authentication check over all decision-relevant fields. Since saved successful packets can be replayed after a restart, identify an additional freshness check.

6. Finish and Submit

  1. Complete Tables 1–4, three evidence groups, and the short conclusion. Each student submits an individual report as a PDF. Use flags only from the target's serial output; the helper never awards flags.
  2. Rotate decoder, packet operator and recorder roles. After completion, green stays on until a valid RSET or physical restart. HELP reports completion; other input leaves it intact. Save all evidence before replaying or resetting.
  3. Close Serial Monitor and unplug USB before moving wires. Report connection or wiring faults before continuing.

Why This Lab Matters

  • A public error check can detect accidental corruption without authenticating a sender
  • A short CRC can be shared by different messages; approving its value does not approve every message with that value
  • Encoding, reliable delivery, authorization, and freshness are separate concerns
  • Test only the assigned controller and supplied maintenance interface

Lab 08 · Week 8 · October 23, 2026

Break the Toy Door: Parity, CRC, and a Whitelist

Investigate a lab-owned Arduino maintenance port, forge commands through three error-check upgrades, and explain why a valid check is not permission

Learning Outcomes

By the End of This Lab

  • Decode hex clues and identify a seven-byte message format
  • Demonstrate a detected one-bit change and an undetected two-bit parity change
  • Create a changed command with a matching CRC using the supplied calculator
  • Find a different command with the same approved CRC while keeping the correct device ID
  • Separate error-check consistency, command acceptance, and authorized origin

The Big Picture

What You Are Doing

  1. Preliminary lab version: the helper and documents are ready for review, but new controller firmware and physical bench tests are still required. Do not use the Lab 7 sampler sketch for this activity.
  2. Scenario: your team has access to a maintenance port on a classroom toy door. A red LED represents LOCKED and a green LED represents OPEN; no real lock is connected.
  3. Recover a leaked service-sheet address from hex output, then use the service sheet to learn the packet format.
  4. Stage 1 checks parity. Stage 2 switches to CRC. Stage 3 also requires the CRC value to appear on an approved list. Each successful stage prints a flag, relocks, and advances.
  5. Use the helper instead of hand-calculating CRC division. A matching check is not a successful Arduino command; record the board's actual serial response.

Before Lab

Preparation

  • Review even/odd parity, CRC purpose, the difference between error detection and authentication, and the idea that hex is encoding rather than encryption.
  • Open the Lab 8 report and packet workbench. Only the computer attached to the Nano needs Arduino IDE and Serial Monitor. Ask the instructor for a prepared computer if the application or board port is unavailable.
  • The instructor must preload and validate the new Lab 8 controller sketch. Do not upload another sketch, inspect firmware for flags, or bypass the protocol by driving LED pins.

Bench Setup

Equipment and Materials

  • Per team: instructor-prepared classic 5 V Arduino Nano and USB data cable
  • Computer with Arduino IDE Serial Monitor and a browser for the packet workbench
  • Breadboard, red LED, green LED, two 330 ohm resistors, and jumper wires, prechecked by the instructor
  • Lab 8 report; approved fallback transcript if the hardware path has not passed its acceptance tests

Follow These Steps

Lab Walkthrough

1. Discover the Maintenance Port — Table 1

Evidence Photo

Save the startup banner and the decoded service-sheet address. No CRC polynomial arithmetic is required.

  1. Keep USB disconnected while checking the instructor's LED wiring. There is one 330 ohm resistor per LED. Use USB power only; no function generator, RF hardware, motor, or actual lock is part of this lab.
  2. Connect USB. Open Serial Monitor at 115200 baud, 8-N-1, with a newline at the end of each message. Do not upload a sketch. Close other programs using that serial port.
  3. Read the startup banner and record device ID, firmware version, stage, and parity convention. If the board still prints Lab 7 sampling data or no supported banner appears, stop and ask the instructor.
  4. Copy the hex-encoded maintenance address into the workbench's converter. Decode it and open that address to recover the service sheet and schematic. Record the decoded address and seven-byte layout; the page is a deliberately supplied classroom prop, not a real leak.
  5. A transmitted line contains 14 hex digits, optionally separated by spaces. The planned Arduino firmware decodes them into seven bytes. Keep the serial setting at 8-N-1: packet parity is checked by the application, not UART hardware.

2. Stage 1: Satisfy Parity — Table 2

Evidence Photo

Preserve one failed parity test and the stage-1 OPEN result. Label the changed bits and record serial text, not color alone.

  1. Capture the supplied valid LOCK message and load its seven bytes into the workbench. Record the parity convention; the final byte must be 00 or 01.
  2. Send the captured LOCK message. It should be accepted while the red LED stays on. A valid message is not necessarily an OPEN command.
  3. Restore that baseline for each test. Flip one bit in the extra byte without changing the parity byte, send it, and record the board's response. Then flip two bits in the extra byte, keep the original check, and test again. Do not alter the device ID or command in these error-pattern tests.
  4. Use the service sheet and converter to build the OPEN command for your own device. Use the helper to write its parity byte, inspect it, and send the packet. Record the flag, LED state, and stage transition before continuing.

3. Stage 2: Recompute the CRC — Table 3

Evidence Photo

Save the changed command with the old CRC failing and the matching new CRC succeeding.

  1. After the upgrade relocks the controller, capture the new valid LOCK frame. Record its payload and CRC. The CRC now covers bytes 0–5, including the extra byte; byte 6 stores the check and is excluded from the calculation.
  2. Change only the four command bytes to OPEN and leave the extra byte and old CRC unchanged. Inspect and send the frame; record the response.
  3. Use Write CRC byte in the helper, inspect the resulting frame, and send it. Preserve the successful flag and transition. This changes both message and check; it is forgery by recomputation, not the fixed-CRC collision required next.

4. Stage 3: Keep an Approved CRC — Table 4

Evidence Photo

Save the approved baseline, a rejected unapproved-CRC attempt, the helper's collision result, and the Arduino's successful stage-3 response.

  1. Capture the stage-3 LOCK frame and record its device ID, extra byte, and approved CRC. Use this team's capture, not another team's result.
  2. Change its command to OPEN while retaining the extra byte. Calculate the new CRC and send that otherwise-valid frame. Record whether its check is valid but unapproved. The whitelist is enforced on the Arduino, not by disabled browser fields.
  3. Restore the approved CRC into byte 6. Set the command to OPEN, then lock every digit except the two digits of the extra byte. The helper's Search extra byte only button sets those locks without changing your values. Both check digits must remain locked.
  4. Run the fixed-CRC search. Record the locked fields, approved CRC, matching packet, and number of candidates tested. One extra byte has 256 possible values; no second extra byte is needed for this specified CRC-8 format.
  5. Confirm that your result is different from the captured LOCK frame, has the correct device ID, still means OPEN, and retains the approved CRC. Send it to the board and record the actual flag, LED state, and final relock.

5. Explain the Trust Boundary

  1. Compare the three protections. Which tested accidental changes did each notice? Why could a deliberate sender still create an accepted OPEN command? Do not claim parity or CRC protects all error patterns.
  2. Explain why a whitelist of CRC values is not a whitelist of complete approved messages. Identify what access the scenario gave your team: permission to use this toy interface, not authority over a real door.
  3. Propose a keyed message-authentication check over all decision-relevant fields. If old valid messages can be replayed, name the additional freshness check. No keyed-firmware repair is implemented or claimed in this preliminary activity.

6. Finish and Submit

  1. Complete Tables 1–4, three evidence groups, and the short conclusion. Each student submits an individual report as a PDF. Use flags only from the target's serial output; the helper never awards flags.
  2. Rotate reader/decoder, packet operator, and recorder roles. Stop after the final relock. Ask the instructor before resetting a board; automatic stage persistence and reset behavior must be confirmed on the final firmware.
  3. Close Serial Monitor and unplug USB before moving wires. If hardware is not ready, use only the instructor-provided fallback and label it as supplied evidence, not a live unlock.

Why This Lab Matters

  • A public error check can detect accidental corruption without authenticating a sender
  • A short CRC can be shared by different messages; approving its value does not approve every message with that value
  • Encoding, reliable delivery, authorization, and freshness are separate concerns
  • Only supplied toy controllers and captures are in scope; no production hardware, networks, or real access-control systems are targets

DC-08 controller: service sheet

Preliminary specification for a lab-owned toy controller. This is the deliberate “leak” in the scenario, not a real access-control product or a secret document. Firmware and physical operation still need instructor validation.

Maintenance connection

The planned maintenance port uses the Nano's existing USB serial connection: 115200 baud, 8-N-1. Send one line of hex text, containing 14 digits, then a newline. Spaces and lowercase hex are allowed. Firmware decodes the text into exactly seven bytes. Do not send the text “OPEN” by itself.

Use Arduino IDE Serial Monitor; do not upload a sketch. Only one program may own the serial port. The packet's application-level parity is independent of the serial setting, which stays 8-N-1 in every stage.

Red means LOCKED; green means OPEN. A valid LOCK command stays red. Serial text—not LED color alone—identifies acceptance or rejection. The LEDs represent a door; there is no lock actuator.

Seven-byte message

ByteMeaningRule
0Device IDOne byte. Must match the connected team's controller.
1–4CommandFour ASCII characters: LOCK or OPEN. Send their hex byte values.
5Extra byte00–FF. Included in the error check; ignored when executing the command.
6Check byteApplication parity in stage 1; CRC-8 in stages 2 and 3.

LOCK is ASCII 4C 4F 43 4B. OPEN is ASCII 4F 50 45 4E. The device ID, extra byte, and check byte are arbitrary bytes and may not display as readable ASCII. Hexadecimal is a representation, not encryption.

Revision notes

Revision 1: parity

Count all one bits in bytes 0–5. Byte 6 must be 00 or 01; only its lowest bit supplies the parity bit and all its other bits must be zero. For even parity the total number of ones, including that bit, must be even; for odd parity it must be odd. Use the convention reported by the controller.

Revision 2: CRC

CRC-8 covers bytes 0–5, including the extra byte but excluding byte 6. Polynomial 07, initial value 00, no input/output reflection, no final XOR. Both the sender and receiver use these exact settings. The helper calculates the value; no polynomial division is required.

Revision 3: approved check values

The developer now requires a valid CRC whose value also appears in an approved-CRC list. The list contains the CRC from the team's captured LOCK message. This is a whitelist of check values, not a whitelist of complete packets or commands. Device ID and command syntax must still be valid.

The extra byte remains ignored by the door application, but it is still covered by the CRC. Is approving a short check value equivalent to approving the message itself?

Planned diagnostic messages

Malformed lines, wrong device IDs, and unknown commands must be rejected. Other outcomes identify parity failure, CRC failure, or a valid CRC not in the approved list. An accepted OPEN command prints the stage flag; then the controller relocks and advances. The final stage relocks after success. Preserve the serial output before the transition.

The connected board supplies its ID, stage, check convention, and baseline capture. If your board does not support this protocol, stop and ask the instructor. The public helper has no target connection or flags.
